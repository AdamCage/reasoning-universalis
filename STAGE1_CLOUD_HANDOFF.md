# Инструкция облачному агенту: Stage 1

Реализуй **Этап 1 спецификации по §7 RESEARCH_PLAN.md: научный дизайн и preregistration**. Не путай его с техническим Stage 0, измерительным Stage 2 или научным пилотом §5.5. Локально выполнена только подготовка; пользователь просит делать Stage 1 в облачном проекте.

## Авторитетные решения и порядок чтения

1. Прочитай `AGENTS.md`, `RESEARCH_SPECIFICATION.md`, `RESEARCH_PLAN.md` вместе с последними дополнениями.
2. Прочитай `design/SELECTED_DECISIONS.json` — фактические решения пользователя; они имеют приоритет над рекомендациями в `design/STAGE1_DECISION_OPTIONS.md`.
3. Прочитай `design/MACHINE_ANNOTATION_PROTOCOL.md`, `design/PREREGISTRATION_DRAFT.md`, `design/hypotheses.json`, `design/SPLITS.md`, `design/E0_PRELIMINARY.json`, `design/G1.json`.
4. Для ограничений исполнения изучи `reports/PRE_PILOT_REVIEW_RESPONSE.md`, `reports/MEASUREMENT_DEVELOPMENT.md`, `design/PILOT_COHORT_ADMISSION.md` и literature addendum.

Подготовленный набор связан hashes в `design/STAGE1_PREPARATION_MANIFEST.json`: проверяются bytes Git blobs, а не рабочие CRLF-файлы. Это manifest передачи, не утверждённый G1; после изменений облачный агент готовит новый approval manifest.

`cursor_objective.md` — историческое задание Stage 0, не текущая инструкция. В частности, оно не даёт основания переписывать спецификацию или повторять весь Stage 0.

## Что выбрано

- Первая статья охватывает H1–H7. Старый совет ограничиться H1–H3 как объёмом статьи не выбран. Основное семейство статистических проверок H1–H3 принято отдельно по рекомендациям; для H4–H7 конкретный confirmatory/secondary/exploratory статус задать в preregistration, не приравнивать охват статьи к одному большому семейству тестов.
- Cluster-first: сначала состояния на development, затем функциональная интерпретация. Не навязывать восемь кластеров; исходные восемь ролей остаются неизменной рабочей онтологией спецификации для сопоставления.
- Консервативные task roots; новая семья × новые roots; S1/S2/S3; предварительные E0 targets с пересмотром только на development.
- Разметка — только ансамбль DeepSeek-V4.1-Flash: 3–5 голосов, фиксированные seeds, повтор с другими seeds без большинства. Это разрешённое пользователем исключение для LLM-разметчиков, не разрешение создать других coding/reviewer/writing агентов. Человеческая валидация отложена по прямому выбору пользователя, **E0 не пройден**.
- Метрики и статистический подход — рекомендации, перечисленные в selected decisions. Это выбранные направления дизайна; окончательные числа/контрасты/процедуры G2 пока не заморожены.
- Утверждающий G1 — `AdamCage`, владелец репозитория. Имя назначено; статус текущего `design/G1.json` pending.

## Работы и необходимые выходы Stage 1

1. Заверши конкретный preregistration: отдельно для H0–H7 точная исходная формулировка, поддержка, опровержение, наблюдаемые признаки, допустимые/недопустимые выводы, выбранные кандидаты метрик и все девять полей §11.2. Не переопределяй H2 только как прогноз или H7 только как ретроспективное обрезание.
2. Сохрани неизменные гипотезы. Окончательные поля, которых спецификация не задаёт, оставь «не задано спецификацией; решение отложено до заморозки протокола». Выбранные пользователем кандидатуры помести рядом как design choices, не подменяй ими финальный G2-протокол.
3. Опиши cluster-first discovery, nested grouped folds, выбор числа состояний, функциональное сопоставление и заморозку mappings без target-family/test leakage. Явно отдели машинное согласие от валидности измерителя.
4. Подготовь завершённый протокол машинной разметки: конкретный размер панели из 3–5, seed schedule, конечное число повторов, schema/prompts, обработка ошибок/разногласий, raw provenance, проверка повторяемости и расчёт стоимости. Предложенные 5 голосов/2 раунда — engineering-кандидат, а не уже утверждённые пользователем числа. Не вызывай RouterAI на Stage 1.
5. Уточни splits и зависимость будущего E0 от человеческой валидации. Исторические шесть roots — development-only. Не создавай выдуманный «собранный» validation/confirmatory-корпус.
6. Конкретизируй **описание** собственного DomainPack `reasoning_universalis_v1` по доступному контракту EpistemeOS: schemas, bindings, external evidence и путь к review/claims. Не реализуй пакет и не меняй demo `risen_universalis_v1` на Stage 1. `measurement/` уже содержит предварительный offline-прототип, не завершённый Stage 2; его фиксированный словарь требует будущей адаптации к cluster-first.
7. Сделай `reports/STAGE1_REPORT.md` с матрицей всех девяти критериев §7 плана, выполненными и открытыми пунктами; подготовь manifest hashes утверждаемого пакета, diff/checks и конкретный пакет для G1.
8. Предъяви пакет AdamCage для утверждения. Не объявляй G1 или весь Stage 1 принятым только по этому handoff или разрешению начать работу. После явного утверждения конкретной версии запиши имя, точный commit/hash набора файлов, дату и основание approval; сохранённые документы должны позволять восстановить утверждённое состояние. G1 не является G2 или независимой человеческой G3.

## Контроль и облачная среда

- `.cursor/environment.json` использует `bash .cursor/install.sh` и `bash .cursor/start.sh`; не меняй установку попутно. Cloud secret `ROUTERAI_API_KEY` может материализоваться в gitignored `.env`. Наличие ключа не разрешает сетевые эксперименты на Stage 1. Не печатай ключ, env или Authorization.
- Для плана будущих расходов учитывай прежний Ledger из опубликованного ZIP и неизвестные стоимости, а не только подтверждённые 0.4165 RUB. Пустой `.research` новой облачной машины не восстанавливает полный бюджет автоматически. Платный запуск требует согласованного состояния общего бюджета и отдельного последующего этапа.
- Из корня: `python3 -m unittest discover -s tests -v` (Python ≥3.11; при отсутствии команды использовать установленный runtime, например `uv run --python 3.12 --no-project ...`). Offline demo: `python3 -m measurement.demo`; это проверка импорта, не E0. Ядро тестируется из `EpistemeOS`: `uv run python -m unittest discover -s tests -v`, если нужны изменения интеграции.
- Убедись, что исходники/тесты/README/AGENTS EpistemeOS и научная спецификация не изменены. Stage 0 исправлен; ZIP позволяет офлайн пересчитать 32 попытки, 6/6, 105 старых сегментов, 210 векторов. Для 35 векторов `parasail-bge-m3` идентичность не подтверждена. Новый offline S2-прототип даёт 95 сегментов, это другая конфигурация.
- Контроль спецификации: Git blob `a9db63e35b389004e0cb5a62ea740dc999927907`; SHA-256 UTF-8 с CRLF→LF `a776fbd34d4a0a8172127debe71395f94c8586af187400200bfe847000dd26ee`. Используй явно именованные hashes; старый SHA-256 CRLF-файла отличается только окончаниями строк.
- Не начинай платный ensemble, новый допуск когорты, генераторы/сбор пилота, Stage 2/3, основной корпус, live stopping или публикацию статьи в рамках этого задания. Укажи точные следующие условия, а не обходи их.

## Критерий завершения задания

Готов конкретный проверяемый дизайн Stage 1, выбранные решения прослеживаются к selected decisions, все гипотезы сохранены, нет ложной human validation/E0/scientific approval, описание DomainPack соответствует ядру, G1 оформлен после утверждения AdamCage. До G1 сообщай «дизайн подготовлен, Stage 1 ожидает утверждения».
