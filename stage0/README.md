# Технический Этап 0

После ревью добавлены строгая привязка допуска и отказ при невалидных embeddings. Старый review, содержащий только hash ответа, больше не допускает платный пилот. Нужны `request_path`, `request_sha256`, `response_path`, `sha256`, `provider`, `full_visible_trace: true` для каждого кандидата. Provider должен совпадать с ответом пробы и последующими ответами; при смене маршрута необходим новый review. Полная проверка выполняется до сети.

`summary.json` различает `process_completed`, `technical_criteria_met`, `failed_requirements` и пригодность каждого наблюдения `analysis_usable`. Технический успех пилота требует пригодных трасс и обоих эмбеддингов для каждой задачи. CLI возвращает 1 при невыполненных критериях, сохраняя результат. При preflight недоступный кандидат фиксируется как исключённый; обязательны оба эмбеддера и хотя бы один кандидат видимой трассы.

HTTP сохраняет `body_base64`, hashes и `body_storage`, отдельно текст/JSON/ошибки. Редактирование секрета выполняется до base64 и явно маркируется; оригинал с секретом не сохраняется. Это правило относится к новым запускам: исторические ответы содержат только декодированный текст. Простая сегментация остаётся инструментом технической проверки и требует научной валидации.

Независимая проверка исторического пакета без `.env` и сети:

```powershell
python -m stage0.evidence --verify evidence/stage0-2026-10-12.zip
```

Экспорт локальных артефактов: `python -m stage0.evidence --export evidence/stage0-2026-10-12.zip`. Перепроверка выявляет 35 векторов с неподтверждённой идентичностью; детали и ограничения — [ответ на ревью](../reports/PRE_PILOT_REVIEW_RESPONSE.md).

Реализация живых проб RouterAI и малого прогона на шести фиксированных задачах. Не выполняет пилот §5.5, проверку гипотез, confirmatory-анализ или заморозку научного протокола. Ядро EpistemeOS не изменяется; его Store используется для хранения артефактов по содержимому. Протокол технического запуска — `context.json`, научные статусы не присваиваются.

Из корня репозитория, Python ≥ 3.11:

```powershell
python -m unittest discover -s tests -v
python -m stage0.runner
python -m stage0.runner --live
python -m stage0.runner --live --review .research/reasoning-universalis/trace-review.json
python -m stage0.audit
```

Без `--live` проверяется только конфигурация. Первый живой запуск выполняет две пробы каждого кандидата и по одной пробе обоих эмбеддеров. Второй требует отдельного файла проверки трассы, связанного SHA-256 с сохранённым ответом. В нём явно задаются `scope: technical_probe_trace_review`, `models`, а для каждой модели — `full_visible_trace`, `response_path`, `sha256` и основание проверки. Отсутствующие, краткие, зашифрованные и оборванные трассы не допускаются. Текст обычного ответа не превращается в reasoning trace.

В малом прогоне используется 5 или 6 задач всего, один ответ на задачу каждой допущенной модели. `RU_TASKS_PER_DOMAIN` и `RU_SAMPLES_PER_TASK` сохранены в контексте, но относятся к будущему дизайну и не расширяют этот прогон. По трассе выполняется простая сегментация; оба разрешённых эмбеддера обрабатывают те же сегменты. Успешность проверяется детерминированным разбором финального маркера, без LLM-судьи. Семантических состояний и научных метрик здесь нет.

Сырой HTTP body, заголовки ответа, параметры, usage, формат reasoning, ошибки, модели, доступные сведения о маршруте, версии исходников и hashes сохраняются под `.research/reasoning-universalis/stage0/`. Ключ удаляется, если сервис отразил его в ответе; это единственное допустимое изменение сохранённого raw body. Артефакты дублируются в content-addressed Store EpistemeOS. `.env`, Authorization запроса и сам ключ туда не попадают.

Запросы последовательные, без автоматических повторов. Lock исключает два одновременных запуска в одном research root. Общий журнал `.research/reasoning-universalis/stage0-budget.json` сохраняет резервы между перезапусками. Неизвестная стоимость, HTTP-ошибка и обрыв не освобождают резерв. Перед запросом резервируются максимум опубликованных тарифов всех endpoint модели, UTF-8 байты входа с запасом на шаблон, предел выходных токенов и коэффициент 2. Если идентификатор отсутствует, диагностическая проба ограничена 128 выходными токенами и использует максимальный опубликованный тариф текстовых моделей каталога. При превышении потолка дальнейшие запросы запрещены.

Это консервативный локальный контроль планируемых расходов, а не гарантия биллинга внешнего сервиса: тарифы и маршруты могут измениться после проверки, а стоимость ошибочного запроса может не сообщаться. Фактический `usage.cost` записывается отдельно от резервов. При обрыве запись `pending` сохраняется и повтор автоматически не делается. Потолок бюджета следует дополнительно ограничивать в кабинете RouterAI, если нужен независимый предел биллинга.

Один ответ с `finish_reason=stop`, полем `reasoning.text` и reasoning-token usage даёт свидетельство полной **видимой** трассы этого ответа после чтения. Это не доказательство полного внутреннего вычисления и не гарантия всех будущих маршрутов. Каждый новый ответ проверяется заново; условия маршрутизации и квантизации остаются ограничениями воспроизводимости.
